Both SSDs were previously documented as "512 GB SATA SSD," which is wrong for both — they are
different capacities, different vendors, and materially different drives (see the SMART
baseline below). Corrected 2026-08-17 from the drives' own identity strings.

**Device letters drifted, and the UUID-addressed mounts held.** These are the same two drives
registered in Phase 2 as `/dev/sdc` and `/dev/sdd`; as of 2026-08-17 they enumerate as
`/dev/sdg1` and `/dev/sdh1`, six positions later. Both Proxmox directory storages mounted
normally with no intervention, because the systemd `.mount` units generated by Disks →
Directory address the filesystems by `/dev/disk/by-uuid/`. Recorded as **evidence, not as a
hypothetical argument**: this is the second time in this lab that device letters moved and
stable identifiers did not (the first being echo-base's pool, created against
`/dev/disk/by-id`). Working hypothesis for the six consumed letters, ~80% confidence: the host
briefly enumerates the ASM1064's six SATA drives at boot before `vfio-pci` claims the
controller. Detail in [phases/phase-6-inquisitor-wazuh.md](../phases/phase-6-inquisitor-wazuh.md).

**Hostname note — three identities, all deliberate.** executor's **OS hostname is `pve`** (the
Proxmox install default); its **lab name and Wazuh agent name are `executor`**; and its agent
connects from **10.0.30.2**, the VLAN 30 storage leg. The node was deliberately not renamed:
renaming a PVE node means relocating `/etc/pve/nodes/pve/` and fixing storage and job
references for no functional gain, whereas Wazuh agent names are arbitrary and set at enrolment
(ADR 0020). Expect the mismatch to show up in the Proxmox UI, the Wazuh agent list, and alert
source addresses; it is not a misconfiguration.

### SSD SMART baseline — 2026-08-17

Both drives **PASSED** self-assessment, with zero reallocated sectors, zero program/erase
failures, zero uncorrectable errors, and zero CRC errors on each.

| Drive | Storage | Power-on hours | Host writes | Life remaining | Notes |
|---|---|---|---|---|---|
| Crucial BX200 480 GB | `ssd-inquisitor` | 11,318 | 44.7 TiB | 94% | WAF ≈1.95× (measured from the TLC/SLC write counters); 137 power-off retracts |
| Samsung 860 EVO 500 GB | `ssd-vmstore` | 4,466 | 5.6 TiB | ~99% | 62 power-on-reset recovery events |

**The BX200 is the lab's weakest storage device** — roughly 2.5× the hours, 8× the host writes,
and a known weakness in sustained steady-state writes. It nevertheless keeps `ssd-inquisitor`:
Wazuh writes ~200 MB/day against ~68 TB of remaining endurance, the heavier sustained writer
(nightly vzdump) is already on the Samsung, and index data is expendable by ADR 0019 while
ssd-vmstore holds the only local copy of the router and NAS configs (ADR 0009). Reasoning in
full in the Phase 6 log.

**Its SMART self-assessment cannot fail, so monitoring must read raw values.** Every threshold
on the BX200 is `000` except attribute 169, and the normalized VALUE column is frozen at 100
while 169's raw value has already moved to 94. A normalized value can never fall below a
threshold of zero, so any tool reading normalized values reports a perfect disk indefinitely —
right up to the point the drive stops answering. The Samsung, by contrast, carries real
Pre-fail thresholds of `010`. Any SMART alerting on this drive reads **raw** attribute values.

**Replacement trigger:** attribute 169 raw value below **80**, or **any nonzero value** in
attributes 5, 181, 182, or 199.

### GPU — XFX RX 5700 DD Ultra 8 GB (→ cantina)
XFX RX 5700 DD Ultra 8 GB (board RX-57XL8L V1.2) — Navi 10, non-XT (36 active CUs),
VBIOS `113-1702NAVI10XL8GD6_MS_190612_W8`. Requires 8-pin + 6-pin aux power — unplugged
aux leads were the root cause of the card's original non-enumeration. No FLR; D3cold
disabled via udev (runbooks/pcie-passthrough.md, GPU addendum). PCIe atomics are
unavailable through QEMU — irrelevant to VA-API transcode, relevant only to any future
ROCm use.

Four PCI functions, all in IOMMU group 2 (the card carries an on-die PCIe switch):

| PCI addr | Function | Device ID | Disposition |
|---|---|---|---|
| 01:00.0 | PCIe upstream port | 1002:1478 | host (`pcieport`) — bridge, never passed |
| 02:00.0 | PCIe downstream port | 1002:1479 | host (`pcieport`) — bridge, never passed |
| 03:00.0 | GPU | 1002:731f (subsys 1682:5705) | → cantina (VM 106) |
| 03:00.1 | HDMI audio | 1002:ab38 | → cantina (VM 106) |

## Controllers & drive mapping
SSDs + NVMe stay on the motherboard SATA controller (Proxmox-owned). All 12 HDDs sit on
two add-in controllers passed through whole to archives.

| Controller | PCI ID | IOMMU group | Owner | Drives |
|---|---|---|---|---|
| Intel Q170 SATA (AHCI) | 00:17.0 | 5 | Proxmox host | 2× SATA SSD (500 GB + 480 GB) |
| RTL8125 2.5 GbE NIC | 05:00.0 | — | Proxmox host | — (LAN trunk, `enp5s0`) |
| ASM1064 SATA | 07:00.0 | 15 | archives (passthrough) | 6× 4 TB SATA |
| Broadcom SAS3008 HBA | 08:00.0 | 16 | archives (passthrough) | 6× 4 TB SAS |
| Samsung NVMe | 09:00.0 | 17 | Proxmox host | boot / VM disk |

Addresses are post-Phase 4: when the GPU began enumerating (buses 01–03), everything
behind it shifted — ASM1064 / SAS3008 / NVMe moved from 05/06/07 to 07/08/09, and
archives' hostpci entries were corrected to match. PCI addresses encode topology;
re-verify them (and NIC names) after any hardware change.

**2026-08-11 — SAS drive replacement.** Serial PBG7ZLHX (HGST HUS724040ALS640) FAULTED with
unrecovered read errors surfaced by the weekly scrub, and was replaced by PEJSRYWX
(HGST HUS72404CLAR4000 — the EMC-branded variant of the same Ultrastar 7K4000). Cold-swapped
into the same physical slot, where it took over the device name `sdd`; the pool resilvered
with 0 errors. Logical block size was verified as 512 bytes with `sg_readcap --long`
**before** installing — ex-array enterprise SAS drives, EMC-branded ones especially, are
frequently 520-byte formatted and unusable by ZFS without a multi-hour `sg_format`. Full
write-up in [phases/phase-5-vault-immich.md](../phases/phase-5-vault-immich.md).

PBG7ZLHX was never individually mapped to a row in the table above, so the removed drive
cannot be pinned to a specific line — and two models plus one serial in the SAS group are
still unconfirmed. Re-confirm the whole SAS group against TrueNAS → Storage → Disks at the
next opportunity.

## ZFS pool

2 simultaneous failures per vdev. TrueNAS boot/system is the 32 GB SCSI vdisk on the NVMe,
not in the pool.
